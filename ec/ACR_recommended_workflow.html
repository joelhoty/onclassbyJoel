1. 核心概念剖析：為什麼需要「實戰整合版」ACR 流程？

在 ACR_b02.md 中，定義了以實作出發的 ACR（Agents → Coding → Review） 學習循環：由指導者建立可運作的起點與明確任務，學生透過 Agent 核對條件（A）、協作完成單一可驗收功能（C），最後從實機畫面出發「往下讀程式、往上懂系統」（R）並留下學習證據。

回顧我們在 ec/ 工作區累積的實務經驗，早期純硬體實作的「六階段漸進式開發 SOP」（arduino_development_workflow_methodology）與近期的 NodeMCU-32S 實作演進（1110-1 → 1112-1 → CODE_REVIEW → 1117-1），正好能無縫對應到 ACR 的每一個環節：

3. 三階段標準作業流程（SOP）與歷次筆記對照

階段 A Agents：硬體先行、環境核對與單元隔離驗證

核心原則：「不要同時測試兩件未知的事物」，軟體必須建立在已驗證的電氣與環境起點上。

  1. 硬體先行與實體拍照留存：斷電接線，先查晶片型號與電壓（ESP32 GPIO 僅耐壓 3.3V；加熱型 SEN0159 接 5V VIN 並共地）；核對腳位衝突（Wi-Fi 與 ADC2 互斥，類比改接 ADC1 如 GPIO 32；I2C 預設 SDA=21, SCL=22）；手機俯拍線色、排針標示與模組背面型號（SSD1306 vs SH1106）。
  2. 環境與程式庫盤點：記錄板型（NodeMCU-32S）、核心版本、函式庫版本（U8g2、DHT_Unified、Adafruit_Sensor）與序列埠鮑率（115200），請 Agent 列出已確認與待查證清單。
  3. 單一元件隔離測試：先單獨跑感測器範例（於序列監控視窗觀察實測變化），再單獨跑 OLED 範例；若沿用既有配置，重現上一輪成功輸出即可。
💬 建議 A 階段首問模板 
這是我目前的開發板、硬體接線、俯拍重點與已安裝程式庫資訊：[附上板型/腳位/程式庫/基礎範例]。
1. 請對照範例與接線，列出我上電前必須核對的電氣與設定項目（包含電壓準位、腳位衝突如 ADC1/ADC2、驅動 IC 差異如 SSD1306/SH1106），並標出資料中缺少的待查證資訊。
2. 請分別給我感測器與顯示器的「單一元件隔離測試」步驟，以及通過時在序列監控視窗（Serial Monitor）與 OLED 上應該看到的明確輸出。
我會先核對實體接線並回報實測結果，全部通過後再進行整合。
✅ A 階段完成標準：能重現基礎輸出、保存接線紀錄與基礎程式快照，並明確列出哪些硬體/環境條件已驗證通過。

階段 C Coding：小步增量、先預測再實測與版本留存

核心原則：「一次只加一項可驗收的功能」，先寫預測再實測，任何改動都保留可回復的上一版。

  1. 將需求轉為可視化驗收條件與最小修改範圍：明定「新增什麼」與「必須保留什麼」；涉及 WebServer 或動畫時，明確要求以 millis() 非阻塞排程取代 delay()；涉及 OLED 排版時先驗證像素座標。
  2. 要求 Agent 交回「四項必要內容」：(a) 可編譯完整程式與註解、(b) 修改位置與前後差異、(c) 尚未確認的假設、(d) 可還原的固定輸入測試方式。
  3. 先寫預測表，再實機驗證：先預測邊界輸入（29/30/31°C 與 NAN），再實測比對。測完後務必恢復真實感測器讀取並確認新舊功能皆正常。
💬 建議 C 階段首問模板 
請以我附上這份已在 NodeMCU-32S 實測通過的程式為起點：[附上基礎 .ino 與硬體摘要]。
本輪只新增一項功能：[描述看得見的結果，例如：有效溫度 >= 30°C 時在 OLED 顯示提醒，低於 30°C 關閉]。
限制條件：
1. 保留現有接線、程式庫、原本的溫濕度/序列輸出與非阻塞排程架構。
2. 請交回：(a) 可編譯完整程式與註解、(b) 修改位置與前後差異、(c) 尚未確認的假設、(d) 一種可透過單一旗標切換、方便還原的固定輸入測試方式（用來測 29/30/31°C 與異常值）。
我會先檢查差異並寫下預測，再編譯上傳與實測。
✅ C 階段完成標準：完成「預測 vs 實測」對照表、恢復感測器實測正常、備份修改前/後兩個可編譯版本（如 v1_base.ino 與 v2_alert.ino）。

階段 R Review：從實作觀察「往下讀程式、往上懂系統」

核心原則：「先有自己的解釋，再請 Agent 給定位提示；區分靜態推演與實機證據」（整合 ACR_b02.md 與 CODE_REVIEW.md）。

  1. 步驟 0：先寫「我的預測 / 我的解釋」：挑一筆實機觀察，先自己找相關區段並說出推論，再向 Agent 求證。
  2. 往下拆解：建立區段地圖、追蹤單筆資料流（讀值 → isnan() → 變數 → if → 顯示）、破解魔術數字（如 _1_HW_I2C、Glyph 67、人為門檻）。
  3. 往上追問：釐清程式庫職責、硬體限制（DHT 2 秒間隔、MG-811 預熱、ADC2 衝突）與異常處理（NAN 或斷線是否誤導使用者）。
  4. 只提單一可驗證改善建議：不讓 Agent 直接重寫整份程式，由學生決定是否走選做改寫或留待下一輪。
💬 建議 R 階段首問模板 
我剛剛實測 [輸入條件，例如 30°C] 時，在 OLED/網頁上觀察到 [實際現象]。
我自己的解釋是：[先寫一兩句自己的推論與懷疑的程式位置]。
請依以下規則協助我做 Review（不要直接改寫整份程式）：
1. 【往下】先只指出我應該檢查的區段、函式與關鍵條件（含不直覺的常數或 API），等我追蹤完再補充細節。
2. 【往上】幫我檢查程式是否有處理感測器讀取失敗(NaN)、逾時或硬體限制，並明確區分「從程式碼可確認的行為」與「必須靠實機測試才能查證的行為」。
3. 若發現值得改善的地方，請只提供 1 項最優先建議與其驗收方式，等我決定後再討論改寫。
✅ R 階段完成標準：能用自己的話解釋「一筆資料流 + 一個關鍵判斷 + 一項軟硬體限制」，並記下 1 個待查證問題或改善想法。

4. 選做改寫與卡住時的退回排查機制

4.1 選做改寫（Review → C 的微循環）

  1. 用 Review 證據定義新需求：例如把門檻從 >= 30.0 改為嚴格大於 > 30.0。
  2. 先預測哪一筆測試值會改變：在 29 / 30 / 31°C 中，只有 30°C 從開啟變關閉。
  3. 最小修改 + 同組資料重測：驗證「該變的有變、不該變的沒壞」。
  4. 邊界規則：若涉及新增元件或改動接線，不可走選做微循環，必須進入下一輪階段 A。

4.2 卡住時回到有證據的地方（整合排錯矩陣）

遇到的異常現象 退回／停留階段 立即執行的證據排查動作
OLED 不亮、全黑、畫面左移 2px 或右側有雜訊線 回到 A 斷電查供電/共地與 SDA(21)/SCL(22)；跑 I2C Scanner 查位址（0x3C/0x27）；檢查 1.3" 面板是否需把 SSD1306 改為 SH1106 建構子。
DHT 頻繁回傳 NaN 或數值不更新 回到 A / C 查 DATA 腳位與上拉電阻；確認取樣間隔 ≥ 2000 ms（DHT22）或 ≥ 1500 ms（DHT11）。
開啟 Wi-Fi 後類比感測器讀值異常或當機 回到 A 檢查是否誤接 ESP32 ADC2 腳位；改接 ADC1（如 GPIO 32）並確認感測器供電（如加熱器改接 5V VIN）。
新功能未通過，或原本正常的功能壞掉 留在 C 立即切回上一版可運作 .ino 確認硬體沒壞，縮小程式碼差異，帶著「操作 + 預期 + 實測 + 錯誤訊息」回報 Agent。
網頁打不開或跑馬燈每 2 秒停頓一次 留在 C 檢查 loop() 是否殘留阻塞式 delay(2000)，改用 millis() 非阻塞排程確保 server.handleClient() 高頻輪詢。
程式能跑，但 Review 看不懂或 Agent 解釋與實測不符 留在 R 核對雙方看的是否為同一份 .ino 版本與硬體條件；從一筆看得見的輸出出發，要求 Agent 一次只給下一個函式位置。
想一次加三個功能（換面板 + 加 CO2 + 網頁折線圖） 回到指導者 拆分為多輪 ACR，本輪只選一項有明確驗收條件的目標，其餘記入「下一輪想法」。

範例程式碼（acr_temp_alert_template.ino）

💻 C++ / Arduino — NodeMCU-32S + DHT22 + U8g2 OLED（支援固定輸入測試與一鍵還原） 
// ============================================================================
// acr_temp_alert_template.ino — ACR 階段 C 標準示範骨架
// 功能：非阻塞讀取溫度，當有效溫度 >= 30.0°C 時於 OLED 顯示高溫提醒
// 特色：內建 USE_FIXED_TEST_INPUT 測試開關，方便驗證 29 / 30 / 31°C 與 NAN 邊界
// 硬體：NodeMCU-32S | DHT22 -> GPIO 16 | OLED I2C -> SDA(21), SCL(22)
// ============================================================================

#include <Arduino.h>
#include <Wire.h>
#include <U8g2lib.h>
#include <Adafruit_Sensor.h>
#include <DHT.h>
#include <DHT_U.h>

// ---------- 1. 硬體腳位與門檻常數 ----------
#define DHTPIN                16          // DHT22 單線資料腳接於 GPIO 16
#define DHTTYPE               DHT22       // 感測器型號（若為 DHT11 請改此處）
const float TEMP_THRESHOLD  = 30.0f;      // 本輪自訂提醒門檻（°C）
const unsigned long READ_MS = 2000UL;     // DHT22 最小安全取樣週期（2 秒）

// ---------- 2. C 階段「可還原固定輸入測試」開關 ----------
// 1 = 啟用固定輸入輪播（依序測試 29.0, 30.0, 31.0, NAN）
// 0 = 恢復真實 DHT 感測器讀取（交付前務必改回 0 並實機複測！）
#define USE_FIXED_TEST_INPUT  1

// ---------- 3. 驅動物件初始化 ----------
// 注意：若使用 1.3 吋 SH1106 面板且出現右邊雜訊線，請改用 U8G2_SH1106_...
U8G2_SSD1306_128X64_NONAME_1_HW_I2C u8g2(U8G2_R0, /* reset=*/ U8X8_PIN_NONE);
DHT_Unified dht(DHTPIN, DHTTYPE);

// ---------- 4. 共享狀態變數 ----------
unsigned long lastReadTime = 0;
float currentTemp          = NAN;
bool  isTempAlert          = false;

#if USE_FIXED_TEST_INPUT
const float TEST_CASES[]   = {29.0f, 30.0f, 31.0f, NAN};
const int   TEST_COUNT     = sizeof(TEST_CASES) / sizeof(TEST_CASES[0]);
int         testIndex      = 0;
#endif

// 判斷是否觸發提醒（Review 選做改寫時，只需聚焦修改此函式的 >= 條件）
bool evaluateTempAlert(float tempC) {
  if (isnan(tempC)) {
    return false; // 讀取失敗時不可誤觸高溫提醒
  }
  return (tempC >= TEMP_THRESHOLD);
}

// 繪製 OLED 畫面（採 U8g2 Page Buffer 分頁繪圖，節省 RAM）
void renderOLED(float tempC, bool alertOn) {
  u8g2.firstPage();
  do {
    u8g2.setFont(u8g2_font_helvB12_tf);
    u8g2.setCursor(0, 18);
    if (isnan(tempC)) {
      u8g2.print("T: Sensor ERR");
    } else {
      u8g2.print("T: ");
      u8g2.print(tempC, 1);
      u8g2.print(" C");
    }

    // 繪製分隔線與提醒狀態列
    u8g2.drawHLine(0, 28, 128);
    u8g2.setFont(u8g2_font_8x13_mf);
    u8g2.setCursor(0, 46);
    if (isnan(tempC)) {
      u8g2.print("STATUS: CHECK DHT");
    } else if (alertOn) {
      u8g2.print("ALERT: >= 30.0 C!");
    } else {
      u8g2.print("STATUS: NORMAL");
    }

    // 底部提示目前是否為測試模式，避免忘記還原
    u8g2.setFont(u8g2_font_6x10_tf);
    u8g2.setCursor(0, 62);
    u8g2.print(USE_FIXED_TEST_INPUT ? "MODE: FIXED TEST" : "MODE: LIVE SENSOR");
  } while (u8g2.nextPage());
}

// 取得溫度（依編譯旗標切換固定測試值或真實感測器）
float acquireTemperature() {
#if USE_FIXED_TEST_INPUT
  float val = TEST_CASES[testIndex];
  testIndex = (testIndex + 1) % TEST_COUNT;
  return val;
#else
  sensors_event_t event;
  dht.temperature().getEvent(&event);
  return event.temperature; // 若讀取失敗，Adafruit 程式庫會回傳 NAN
#endif
}

void setup() {
  Serial.begin(115200);
  delay(200);
  u8g2.begin();
  u8g2.enableUTF8Print();
  dht.begin();
  Serial.println(F("[ACR] System ready."));
}

void loop() {
  unsigned long now = millis();
  // 非阻塞排程：每 2 秒更新一次，未來可直接加入 server.handleClient() 而不產生延遲
  if (now - lastReadTime >= READ_MS) {
    lastReadTime = now;
    currentTemp  = acquireTemperature();
    isTempAlert  = evaluateTempAlert(currentTemp);

    // 輸出序列監控證據，方便填寫「預測 vs 實測」對照表
    Serial.print(F("Temp="));
    if (isnan(currentTemp)) Serial.print(F("NAN"));
    else Serial.print(currentTemp, 1);
    Serial.print(F(" | Alert="));
    Serial.println(isTempAlert ? F("ON") : F("OFF"));

    renderOLED(currentTemp, isTempAlert);
  }
}

7.1 跨專案防禦性工程檢核表（彙整自歷次 ec/ 實戰地雷）

面向 常見地雷現象 防禦做法（建議直接寫入階段 A/C 檢核）
ESP32 ADC 與 Wi-Fi開啟 Wi-Fi 後類比讀值失效類比感測器一律使用 ADC1（GPIO 32~39），避開被 Wi-Fi 射頻佔用的 ADC2。
電源與耐壓加熱型感測器耗電過大導致 ESP32 不斷重開機，或訊號電壓過高燒毀腳位高耗電模組（如 SEN0159）接 5V (VIN) 並共地；確認回傳至 ESP32 GPIO 的訊號不超過 3.3V。
OLED 驅動 IC1.3" 面板畫面左移 2px、最右側出現亮線檢查背面型號標示與驅動 IC，將 U8G2_SSD1306_... 切換為 U8G2_SH1106_...。
多任務時序網頁連線逾時或 OLED 動畫停頓不流暢loop() 嚴禁長 delay()，改用 millis() 非阻塞排程，同時遵守 DHT 2 秒取樣下限。
封閉區網相依性教室區域網路無對外連線，網頁圖表整片空白內嵌 WebServer 儀表板優先採用免外部 CDN 依賴的原生 HTML5 Canvas / SVG（參考 1117-1）。
AI 假設偏移Agent 順手改掉原本腳位或刪掉既有功能每次 Prompt 明確宣告「保留清單」與「標記未確認假設」，上傳前必做差異比對（Diff）。

7.2 AI 協作常見反模式（Anti-Patterns）與修正對策

  1. 「一次貼上全部需求，讓 Agent 直接產生 500 行程式」：出錯時無法定位硬體或邏輯問題。對策：嚴守「A 單元隔離 → C 單一增量」，超出範圍就拆到下一輪。
  2. 「把靜態讀程式當成實機驗證」：註解、門檻與型號未實測前都只是待查證假設。對策：以實機輸出與固定輸入對照表為唯一驗收依據。
  3. 「跳過『我的預測』直接叫 Agent 解釋整支程式」：容易產生看懂的錯覺。對策：C 階段先填預測、R 階段先寫自己的解釋，再請 Agent 給定位提示。

7.3 教學導入權衡（初學者 vs 進階專題）

  • 初學者（第一、二輪）：指導者提供可運作起點程式、標準首問模板與測試表，聚焦「對照差異、固定輸入測試、說出一筆資料怎麼走到畫面」。
  • 進階專題（第三、四輪以上）：由學生自擬本輪任務與 Prompt，指導者改為把關「範圍是否過大、驗收條件是否具體、新增硬體是否先回 A 驗證」。
